# 09: Input validation and sanitization for client-facing sinks

## Problem Statement

Client-supplied data — request bodies, query string parameters, headers, and dynamic route segments — isn't consistently validated against an expected shape before it's used across the app's 23 API route handlers. Where checks exist at all, they're hand-rolled per route with no shared schema. This isn't just inconsistent: it has concrete consequences today. A malformed `id` in the URL for an item or flashcard (e.g. `GET /api/items/not-a-uuid`) throws an uncaught Postgres error and returns a generic, unhandled 500 instead of a clean 400 — no route or service code catches it, and no test exercises the path. The WebAuthn verification endpoints (`login/verify`, `register/verify`, `invite/verify`, `recover/verify`) pass the raw request body straight into `@simplewebauthn/server` with no shape check of the app's own first — the app never defines what it expects to receive, only the library does. The person operating and maintaining this app wants confidence that "secure by default" isn't enforced ad hoc, one route's improvised checks at a time, and that a malformed request always produces a predictable, safe outcome rather than an information-leaking crash.

## Solution

Introduce Zod as this codebase's schema-validation library — a deliberate, explicitly-called-out amendment to spec 08's earlier decision to keep validation hand-rolled and not add a schema library. That decision was scoped to spec 08's error-handling/logging work, where adding a validation library would have been scope creep; it does not apply to a dedicated validation effort, and this spec should be read alongside spec 08, not as silently overriding it.

Every client-facing sink that's genuinely attacker-controlled — request body, query string, dynamic route segments, and any header actually set by the client — gets an explicit Zod schema checked before the value reaches business logic. Validation is strict and fail-closed: malformed input is rejected outright, never silently coerced or sanitized into something "close enough." Rejections report field-level detail through spec 08's `ValidationError`/`issues` mechanism, once that piece of spec 08 lands — this effort has a hard dependency on it and does not invent a second, parallel error-response shape.

Not everything client-adjacent is in scope. Several sinks were investigated and deliberately excluded because validating their format wouldn't change any actual security property (see Out of Scope). Rollout is prioritized by risk rather than done as one blanket pass across all 23 routes — it starts with the two sinks confirmed to have a concrete failure mode today, not merely a theoretical one.

## User Stories

1. As a maintainer, I want every API route's request body validated against an explicit schema before it reaches business logic, so that malformed input is rejected predictably instead of causing undefined behavior.
2. As a maintainer, I want query string parameters (`limit`, `cursor`, `query`, `kind`, `tags`, `cascade`) validated against explicit schemas, so pagination and filter inputs can't silently misbehave or bypass the existing ad hoc clamping logic.
3. As a maintainer, I want dynamic route segments like `id` validated as well-formed UUIDs before being used in a database query, so a malformed ID returns a clean 400 instead of an unhandled Postgres error and a 500.
4. As a user of the app, I want a request with a malformed item or flashcard ID in the URL to fail with a clear, safe error instead of crashing the server.
5. As a maintainer, I want the WebAuthn verification endpoints to validate the shape of the WebAuthn response body before handing it to `@simplewebauthn/server`, so the app defines what it accepts instead of relying solely on the library's own internal validation.
6. As a maintainer, I want invalid input rejected outright rather than sanitized or coerced into a valid shape, so a malformed request never silently becomes a different, unintended request.
7. As an API consumer (the app's own frontend), I want validation failures to return field-level detail, so forms can show the user exactly what to fix.
8. As a maintainer, I want validation failures to flow through spec 08's `ValidationError`/`issues` mechanism and `withErrorHandling` wrapper, so validation errors and other not-happy-path errors share one consistent response envelope.
9. As a maintainer, I want Zod schemas colocated with the route they validate, so a route's accepted input shape is visible next to its handler rather than requiring a jump to a central file.
10. As a maintainer, I want shared validation primitives (a UUID param schema, a pagination/limit schema, a tag-array schema) factored into a shared module once duplicated across routes, consistent with the existing `src/lib/request-fields.ts` pattern, so common shapes aren't redefined per route.
11. As a maintainer, I want TypeScript types for request data inferred from the Zod schemas (`z.infer`) rather than hand-written separately, so the schema is the single source of truth and the two can't drift apart.
12. As a maintainer, I want this effort's rollout prioritized by risk rather than applied to all 23 routes in one pass, so the highest-consequence gaps are fixed first and each change can be reviewed carefully.
13. As a maintainer, I want the WebAuthn response body schema and the `[id]` UUID param schema treated as top priority, since both are confirmed gaps with a concrete failure mode today.
14. As a maintainer, I want session tokens, invite tokens, recovery codes, and the WebAuthn challenge cookie explicitly excluded from this effort, since a malformed value already fails safely today via a hash-lookup miss, and format validation would only change the shape of the error, not any actual security property.
15. As a maintainer, I want the header carrying the resolved current user excluded from this effort, since the proxy layer always strips any client-supplied value and injects its own trusted one before forwarding — it isn't attacker-controlled by the time a route handler reads it.
16. As a maintainer, I want this effort scoped strictly to shape/type/format validation of request data, with CSRF protection, security response headers (CSP/HSTS), and rate limiting treated as separate, future efforts rather than folded into this one.
17. As a maintainer, I want this effort's rollout to depend on spec 08's ticket 04 (the `ValidationError.issues` field and `withErrorHandling` wrapper) landing first, so validation errors have a stable, shared place to report field-level detail rather than inventing a second, parallel error-response shape.
18. As a maintainer, I want this effort's dependency on spec 08 scoped narrowly to its error-taxonomy piece (ticket 04), not its unrelated structured-logging/LogTape rollout (tickets 05-07).
19. As a developer, I want each Zod schema covered by unit tests exercising both the valid case and every distinct invalid-shape case, verifying the resulting `ValidationError`/`issues` content, consistent with this repo's existing direct-function-invocation Vitest convention.
20. As a developer, I want the WebAuthn response schema additionally covered by property-based/fuzz testing, given it's the one sink handling structurally complex, attacker-adjacent input where hand-written test cases are least likely to catch every edge case.
21. As a maintainer, I want markdown rendering (item and wiki content) to gain an explicit `rehype-sanitize` step in its rehype pipeline, so the pipeline's current XSS-safety — which today depends on `rehype-raw` simply being absent — is enforced explicitly rather than by omission.
22. As a maintainer, I want `rehype-sanitize` placed before `rehype-prism-plus` in the pipeline, so code-block syntax highlighting continues to work without needing to extend the sanitize schema for the highlighter's generated markup.
23. As a maintainer, I want confirmation, once `rehype-sanitize` is added, that code-block syntax highlighting still renders correctly, since the change is only safe with this specific plugin ordering.
24. As a user pasting a markdown link or image with a `javascript:`/`data:` URL, I want it stripped rather than rendered live — already true today via react-markdown's default URL transform, and unaffected by the `rehype-sanitize` addition.
25. As a maintainer, I want no schema-validation library other than Zod introduced, and Zod's adoption treated as an explicit, called-out amendment to spec 08's prior "no schema library" decision, not a silent contradiction of it.

## Implementation Decisions

- **Validation library**: Zod, introduced as an explicit amendment to spec 08's decision against a schema library — that decision was scoped to error-handling work, not to this effort.
- **Validation philosophy**: strict, fail-closed. Reject non-conforming input outright; no coercion or sanitization to make malformed input acceptable. (The markdown-sanitization decision below is a separate, presentational concern, not an exception to this.)
- **Scope**: request body, query string parameters, dynamic route segments, and any header actually set by the client, across the app's API route handlers.
- **Explicit exclusions, with rationale**:
  - Session tokens, invite tokens, recovery codes, and the WebAuthn challenge cookie — a malformed value already fails closed today via a hash-lookup miss; format validation would change only the error's shape, not any security property.
  - The header carrying the resolved current user — the proxy layer always deletes any client-supplied value and sets its own trusted one before forwarding, so it isn't attacker-controlled input by the time a route handler reads it. Its trustworthiness depends on the proxy's route matcher covering every sensitive route — a separate routing-configuration concern, not part of this effort.
  - CSRF protection, security response headers (CSP/HSTS), and rate limiting — explicitly out of scope, treated as separate future efforts.
- **Priority sinks (tier 1)**:
  1. The WebAuthn verification endpoints' response body — currently passed unvalidated into the WebAuthn library. Gets a schema for the top-level envelope shape (credential id/rawId as base64url strings, a literal type field, the response object) before being handed to the library. This does not duplicate the library's own cryptographic verification (signature, challenge, origin/RP-ID checks) — only the shape is validated at this layer.
  2. Dynamic `id` route segments on the item and flashcard detail routes — currently passed as raw strings directly into a database query against a UUID-typed column, where a malformed value throws an uncaught driver-level error resulting in an unhandled 500. Gets a UUID-format schema applied before the query runs.
- **Rollout order beyond tier 1**: prioritized by risk — auth-adjacent and write endpoints before read-only/low-risk endpoints — not a single blanket retrofit across all routes.
- **Error integration**: validation failures are reported through spec 08's error taxonomy — `ValidationError`, extended with a field-level `issues: [{ field, message }]` list — and returned via spec 08's shared `withErrorHandling` wrapper and response envelope. This effort depends on that piece of spec 08 landing first, and does not build a second, parallel error-response mechanism. It does not depend on or block spec 08's unrelated structured-logging rollout.
- **Schema organization**: colocated per route. Shared primitives (a UUID param schema, a pagination/limit schema, a tag-array schema) are factored into a shared module only once genuine duplication appears across routes, following the pattern already established by the existing shared request-field helpers — not pre-built as a central validation library ahead of need.
- **Type strategy**: TypeScript types for validated request data are inferred from the Zod schemas, not hand-written separately, so schema and type cannot drift apart.
- **Markdown sanitization** (adjacent to, but distinct from, request-input validation): `rehype-sanitize` is added to the shared rehype pipeline used for item/wiki markdown rendering, positioned *before* the syntax-highlighting plugin already in that pipeline. This ordering is deliberate: the tree sanitize operates on, at that point in the pipeline, contains only elements generated from trusted markdown syntax (no raw-HTML node type exists there today, since raw-HTML parsing isn't enabled), and the default sanitize schema already permits the `className` attribute on code elements for the `language-*` convention the highlighter depends on to pick a grammar. The highlighter then runs afterward and injects its own highlighting markup directly into the already-sanitized tree, so its generated class names never need to be added to the sanitize schema. This closes the gap where the pipeline's current XSS-safety depends implicitly on raw-HTML parsing simply never being enabled, rather than being enforced explicitly. Separately, URL-scheme sanitization for markdown links/images (stripping `javascript:`/`data:` URLs) already happens today via the markdown renderer's default URL transform, independent of this change.

## Testing Decisions

- **Seam**: direct function/module invocation via Vitest — import a schema module and call it directly, no HTTP server, matching this repo's existing convention (already used in files like `flashcards/route.test.ts`, `items.test.ts`, and the seam spec 08 established for its own error-handling tests). No new seam is introduced.
- **Coverage**: every new Zod schema gets a unit test covering the valid case and each distinct invalid-shape case, asserting the resulting `ValidationError`/`issues` content.
- **Property-based testing**: the WebAuthn response schema additionally gets fuzz testing via a property-based testing library (a new dependency), specifically because it's the one sink guarding structurally complex, attacker-adjacent input — the class of input where hand-written cases are least likely to anticipate every edge case. No other schema in this effort gets fuzz testing; their shapes (pagination, tag arrays, UUID params) are simple enough that hand-written cases give adequate coverage.
- Once `rehype-sanitize` is wired into the markdown pipeline, manually verify (or add a lightweight test if a seam already exists for markdown rendering output) that code-block syntax highlighting still renders correctly under the new plugin order.

## Out of Scope

- Format/shape validation of session tokens, invite tokens, recovery codes, and the WebAuthn challenge cookie — already fail closed today; validating their format wouldn't change any security property.
- Validation of the resolved-current-user header — it is never client-controlled by the time a route handler reads it, since the proxy layer always overwrites it.
- CSRF protection, security response headers (CSP/HSTS), and rate limiting — separate, future efforts.
- Any change to spec 08's logging/structured-logging rollout — this effort depends only on spec 08's error-taxonomy piece, not its logging work.
- A blanket, single-pass retrofit of all routes at once — rollout is staged by risk instead.
- Cryptographic/protocol-level verification of WebAuthn responses (signature validity, challenge matching, origin/RP-ID checks) — that remains entirely the responsibility of the existing WebAuthn library; this effort only adds a shape-validation layer in front of it.

## Further Notes

This spec was reached via a multi-round `grill-me` interview session, not assumptions. Several rounds relied on fact-finding sub-agents (not the user) to resolve otherwise-guessable details: an inventory of all 23 API route handlers and what each reads from the request; a scan confirming no schema-validation library exists in the codebase today; exact generation formats for every auth-related token/cookie/header (revealing that manually validating their format would provide no actual security benefit, since malformed values already fail safely via a hash-lookup miss); a scan of the markdown rendering pipeline confirming its current XSS-safety depends on raw-HTML parsing being disabled, and that the renderer's default URL transform already sanitizes link/image URL schemes; a check of spec 08's implementation status confirming it is not yet built; and a targeted check of the `[id]` route params confirming a malformed UUID currently produces an unhandled 500, with no existing test covering that path.

Two concrete gaps surfaced during this interview and are the effort's stated priority: the WebAuthn verification endpoints' request body (currently passed to the WebAuthn library with zero app-level shape validation), and the `[id]` route params on item/flashcard detail routes (currently causing an unhandled 500 on malformed input) — both confirmed via direct code inspection, not assumption.

Zod's introduction here is a deliberate, called-out amendment to spec 08's earlier "no schema-validation library" decision, not an unnoticed contradiction of it — this spec should be read alongside spec 08, not as superseding it.
