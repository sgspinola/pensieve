# 08: Centralized error handling, error taxonomy, and structured logging

## Problem Statement

Error handling in Pensieve today is ad hoc. 21 of 23 API route files under `src/app/api/**/route.ts` hand-roll their own `try/catch` and call a partial helper (`toErrorResponse` in `src/lib/api-errors.ts`) that maps three existing error classes (`UnauthorizedError`, `NotFoundError`, `ValidationError` in `src/services/errors.ts`) to status codes but rethrows anything else, letting it fall through to Next.js's default 500; 2 route files (`auth/logout`, `auth/login/options`) have no `try/catch` at all. Several routes still build inline `NextResponse.json({ error: "..." }, { status: 400 })` responses by hand instead of throwing a typed error. There is no way to reliably tell, from the outside, whether a given failure was an expected "not-happy path" (bad input, missing resource, unauthenticated) or a genuine bug — the distinction exists informally in three classes, but nothing enforces it consistently, and unexpected errors aren't guaranteed to produce a safe, generic client-facing message.

On the client, there are no React/Next.js error boundaries anywhere in `src/app` (no `error.tsx`, `global-error.tsx`) — a render crash on any page currently blanks the whole app instead of degrading gracefully.

There is no logging infrastructure at all: no logger library, no structured/leveled output, nothing written to a file in local development, and nothing that could be shipped to CloudWatch or any other destination in production — only scattered raw `console.*` calls. When a single request touches multiple services (e.g. an item update calling into tag and permission logic), there is no shared identifier tying those log lines together, making it impossible to reconstruct what happened for one specific request.

## Solution

Introduce a small `AppError` class hierarchy that both existing and future not-happy-path errors extend, and route every API handler through a single `withErrorHandling` wrapper (built by extending the existing `toErrorResponse`) that maps `AppError` subclasses to a consistent JSON envelope and collapses anything else into a generic, safe 500 — so "expected failure" vs. "bug" becomes structural rather than convention. Add Next.js error boundaries (`error.tsx` per segment, one `global-error.tsx`) so a client render crash degrades gracefully instead of blanking the app.

Replace ad hoc `console.*` calls with **LogTape**, a structured logger with built-in `AsyncLocalStorage`-based context propagation and an official CloudWatch Logs sink. `middleware.ts` stamps every incoming request with a correlation ID; that ID (and other request-scoped fields) is bound once via LogTape's `withContext` and automatically appears on every log line emitted anywhere during that request's lifetime — service calls, route handlers, mutation logging — with no manual threading through function signatures. Sensitive fields (session/auth tokens, WebAuthn credentials, email addresses, recovery codes) are redacted via `@logtape/redaction`. The log destination is environment-driven: a local rotating file in development, stdout in production by default (consumable by a platform log driver on ECS/Fargate/Lambda), with `@logtape/cloudwatch-logs` ready to wire in explicitly once a concrete AWS deployment target is chosen (none exists in the repo today).

## User Stories

1. As a developer, I want a single `AppError` base class with typed subclasses, so that I can distinguish "the user/caller did something the app expects to sometimes fail" from "the app has a bug" with a simple `instanceof` check instead of ad hoc conventions.
2. As a developer, I want the existing `UnauthorizedError`/`NotFoundError`/`ValidationError` refactored onto that base class, so that the taxonomy is consistent without discarding what already works.
3. As a developer, I want every API route to go through one shared `withErrorHandling` wrapper instead of its own `try/catch`, so that error-to-response mapping can't drift route by route.
4. As a developer, I want the 2 routes that currently have no error handling at all (`auth/logout`, `auth/login/options`) brought in line with the rest, so that their failure behavior is explicit rather than accidental.
5. As a developer, I want the inline hand-written 400 responses in routes like `flashcards/route.ts` and `items/route.ts` replaced with real `ValidationError` throws, so that all not-happy-path responses go through the same taxonomy and envelope.
6. As an API consumer (the app's own frontend), I want every error response to share one JSON envelope shape (`{ error: { code, message, requestId? } }`), so that client-side error handling doesn't need per-route special cases.
7. As a user, I want an unexpected server error to show me a generic, safe message with no internal details (stack traces, raw exception text) leaked, so that bugs don't expose implementation details.
8. As a user hitting a validation error, I want field-level detail (which specific field was invalid) where the form can act on it, so that I know exactly what to fix instead of a generic "invalid input" message.
9. As a developer, I want `ValidationError` to optionally carry a list of field-level issues, so that forms can highlight the specific bad input without a broader schema-validation library.
10. As a user, I want a crashed page to show a scoped fallback ("something went wrong, try again") instead of the whole app going blank, so that one broken page doesn't take down my whole session.
11. As a developer, I want per-segment `error.tsx` plus one top-level `global-error.tsx`, so that render crashes are caught at the most local boundary possible.
12. As an operator, I want every server-side log line written as structured JSON rather than free-text `console.*` output, so that logs are filterable and machine-parseable.
13. As an operator, I want logs written to a local file automatically in development, so that I don't need any extra infrastructure to see what the app is doing while working locally.
14. As an operator, I want logs shippable to CloudWatch (or another destination) in production without changing application code, so that deployment target changes don't require a logging rewrite.
15. As an operator investigating an incident, I want every log line produced while handling one HTTP request to share a single correlation/request ID, so that I can filter logs down to exactly the request I care about, even when multiple services logged during that request.
16. As a user who hits an error, I want the request ID surfaced back to me (response header, and inside the error envelope on unexpected 500s), so that I can hand that ID to whoever's debugging it instead of describing "it broke, not sure when."
17. As a developer, I want request-ID propagation handled ambiently (via `AsyncLocalStorage`/LogTape context) rather than passed explicitly through every function signature, so that adding a new logged call site never requires plumbing an ID parameter through unrelated code.
18. As an operator, I want expected/not-happy-path errors logged at `warn` and unexpected errors logged at `error`, so that a future CloudWatch alarm/metric filter can watch the `error` level without being swamped by ordinary 404s/401s/validation failures.
19. As an operator, I want every server log line to carry a consistent baseline (route/method, response status, duration, authenticated user ID, request ID), so that I don't have to re-derive "what happened on this request" from timestamps and guesswork.
20. As an operator, I want mutation operations (create/update/delete on items, flashcards, tags, invites, sessions, recovery codes, WebAuthn credentials) to log the affected entity's kind (where applicable) and ID on every mutation — success or failure — so that I have a lightweight trail of what changed without a separate audit system.
21. As an operator, I want update operations specifically to log which fields changed (by name, not value), so that I can see the shape of a change without the log line containing potentially large or unvetted field content.
22. As an operator, I want sensitive fields (session/auth tokens, WebAuthn credential data, email addresses, recovery codes) automatically redacted from all log output, so that no log line can leak credentials or PII regardless of which call site produced it.
23. As a developer, I want the logging library to work cleanly inside Next.js without special bundler configuration (no worker-thread transport issues), so that adopting structured logging doesn't fight the framework's build pipeline.
24. As a developer, I want service-layer tests for each `AppError` subclass and for the `withErrorHandling` wrapper's status-code mapping, so that the taxonomy's correctness is verified the same way the rest of the service layer already is.
25. As a developer, I want a minimal Playwright smoke spec proving a page that crashes actually renders its `error.tsx` fallback end-to-end, so that a hydration-only bug in the boundary itself would be caught (something an HTTP-level test cannot see).
26. As a maintainer, I want a new `docs/architecture/` page documenting the error-handling/logging design (taxonomy, envelope, correlation ID mechanism, log pipeline), so that the architecture is discoverable without reading the implementation.
27. As a maintainer, I want `docs/flows/` pages whose error-path diagrams are affected by the new envelope/status behavior refreshed via a Trailmark pass, so that flow documentation doesn't silently drift from the new behavior.

## Implementation Decisions

- **Error taxonomy**: new `AppError` base class in `src/services/errors.ts`; `UnauthorizedError` (401), `NotFoundError` (404), `ValidationError` (400) refactored to extend it. No additional subclasses (no `ForbiddenError`/`ConflictError`/`RateLimitError`) — a full scan of every `NextResponse.json({ error }, { status })` across all API routes found only 400/401/404 ever produced in current behavior; adding speculative status codes now isn't warranted.
- **`ValidationError` extension**: gains an optional field-level `issues` list (shape: an array of `{ field, message }` pairs), defaulting to empty for call sites that don't need it.
- **Error `code`**: a machine-readable string derived directly from the `AppError` subclass name (e.g. `NOT_FOUND`, `VALIDATION_ERROR`) — no separate code registry to keep in sync.
- **Response envelope**: `{ error: { code, message, requestId? } }` on every error response. `AppError` subclasses pass through their own `code`/`message`; anything else (an unexpected throw) is collapsed to a generic code/message, with `requestId` included specifically on that generic-500 case so a user can report it.
- **Central handler**: extend the existing `toErrorResponse` (`src/lib/api-errors.ts`) into a `withErrorHandling(handler)` wrapper that every route exports its handler through. It replaces per-route `try/catch`, adds the previously-missing default-500 handling for unknown throws, and is applied to all ~20 route files (including the 2 currently missing any error handling and the routes with hand-written inline 400s).
- **Client-side error boundaries**: `error.tsx` per route segment under `src/app`, plus one root `global-error.tsx`. No client-to-server error reporting — this is UI-fallback only (see Out of Scope).
- **Logging library**: **LogTape**, chosen over an initial pino recommendation specifically because of this project's two hardest requirements — request correlation and CloudWatch shipping — are first-party LogTape features rather than something to hand-build:
  - Correlation: `configure({ contextLocalStorage: new AsyncLocalStorage() })` once at startup; `middleware.ts` generates a request ID (`crypto.randomUUID()`) if the inbound request doesn't already carry one, and the request lifecycle is wrapped in `withContext({ requestId, ... })` so every nested `getLogger(...)` call anywhere in that request's call graph automatically includes it — no explicit parameter threading.
  - CloudWatch: the official `@logtape/cloudwatch-logs` sink (batched, default 1000 events/1s flush, configurable) is the intended integration point once a deployment target is chosen — not wired with real credentials yet, since no AWS deployment target exists in this repo today (no Dockerfile, CDK/SAM/Amplify/Terraform config, or `@aws-sdk/*` dependency).
  - Redaction: `@logtape/redaction`, configured to strip session/auth cookies and tokens, WebAuthn credential fields, email addresses, and recovery codes from any log record before it reaches a sink.
- **Transport selection**: environment-driven, not hardcoded to a specific AWS service. Development uses LogTape's rotating file sink, writing to a local, gitignored log file. Production defaults to stdout (JSON), on the assumption that whatever platform is eventually chosen (ECS/Fargate, Lambda) ingests stdout into CloudWatch via its own log driver at no extra app-code cost. If the eventual target turns out to be something that can't attach a log driver (e.g. a managed host with no log-driver hook), the CloudWatch sink gets wired in explicitly at that point — deliberately deferred rather than guessed at now.
- **Log levels**: `AppError`-derived (expected/not-happy-path) failures log at `warn`; anything else (unexpected/unhandled) logs at `error` — the level a future CloudWatch metric filter/alarm would target.
- **Baseline log fields**: every server log line includes route/method, response status, duration (ms), the authenticated user's ID (not email — email is redacted), and the request ID.
- **Mutation logging**: on every create/update/delete, log the entity's kind (where the entity has one — currently only `items`, via its `CreatableItemKind` field) and its ID, on both success and failure. For update operations specifically, also log which field names changed (not old/new values, to avoid logging potentially large or unvetted field content) — only `updateItem` and `updateFlashcard` need real field-diffing logic; both already fetch the pre-update row (for permission/merge purposes), so the diff reuses that existing read rather than requiring a new query. All other mutations across the service layer (tags, invites, sessions, recovery codes, WebAuthn credentials/users) are create-or-delete only, so they log kind/id with no diff step.
- **Observability scope**: CloudWatch (logs, eventually metric filters/alarms) is the only observability target for this phase — no error-tracking/alerting service (e.g. Sentry) is being integrated now.

## Testing Decisions

Two seams, both reusing this repo's existing conventions rather than introducing new testing infrastructure:

1. **Direct function invocation (Vitest)** — the dominant seam, matching the existing style already used in files like `flashcards/route.test.ts` and `items.test.ts`: import a route handler, service function, or `middleware.ts` function and call it directly, no HTTP server, no mocking of internal collaborators. This seam covers:
   - `withErrorHandling`: invoke a wrapped handler and assert the JSON envelope/status for each `AppError` subclass, plus the generic-500 case for an unexpected throw.
   - `middleware.ts`: call directly with a constructed request, assert it stamps `x-request-id` when absent and preserves an existing one.
   - Service-layer `AppError` throws, extending the taxonomy coverage the existing service tests already provide.
   - **Log content**: register an in-memory LogTape test sink via `configure()` before invoking a handler under test, then assert on the captured records (level, `requestId`, `entityKind`/`entityId`/`changedFields`, confirmation that redacted fields never appear) — observed as a side effect of the same handler invocation, not a separately mocked path.
2. **Playwright** — one smoke spec proving a route that crashes actually renders its `error.tsx` fallback after real render/hydration, per this repo's existing e2e convention (smoke-level only; Vitest never touches a browser). This is the one thing the Vitest seam structurally cannot verify.

No new seam is introduced solely to test logging — it's observed through the same route/handler invocation used for HTTP-response assertions, via LogTape's swappable sink.

## Out of Scope

- New `AppError` subclasses beyond the existing three (`Unauthorized`/`NotFound`/`Validation`) — no current code path produces a 403-distinct-from-401, 409, or 429, so adding them now would be speculative.
- Client-to-server error reporting (e.g. POSTing browser render crashes to a logging endpoint) — `error.tsx`/`global-error.tsx` provide a graceful UI fallback only; the crash itself is not shipped to server-side logs in this pass.
- Any third-party error-tracking/alerting service (Sentry or similar) — CloudWatch logs only, for this phase.
- Actual CloudWatch wiring with real AWS credentials/IAM — no AWS deployment target exists in this repo yet; the `@logtape/cloudwatch-logs` sink is the intended integration point once one is chosen, not part of this implementation.
- Old/new value logging for changed fields on updates — only field *names* are logged, not values.
- A persisted, queryable audit-log store (e.g. a database table of who-changed-what) — mutation logging here is a structured log line through the normal logging pipeline, not a separate audit subsystem.
- A broader schema-validation library (e.g. Zod) — the codebase has none today and this work doesn't introduce one; `ValidationError`'s new field-level `issues` list works with the existing hand-rolled validation functions.

## Further Notes

This spec was reached via a multi-round `grill-me` interview session rather than assumptions. Several rounds relied on fact-finding sub-agents (not the user) to resolve otherwise-guessable details: a scan of the existing error-handling code (surfacing the pre-existing `toErrorResponse` helper and its adoption across 21/23 routes), an AWS-deployment scan (confirming no deployment target exists anywhere in the repo), a Zod/Server-Actions scan (confirming neither is used, simplifying the retrofit scope to API routes only), a mutation-service survey (confirming only `updateItem`/`updateFlashcard` need real field-diffing, and that both already have a reusable before-state read), and a full status-code catalog across all routes (confirming no error subclasses beyond the existing three are structurally needed). The logging library choice was revised mid-session, from an initial pino recommendation to LogTape, after the user asked for it to be evaluated directly against the request-correlation requirement — current LogTape documentation was fetched live to verify context-propagation and CloudWatch-sink claims rather than relying on training-data recall.

Per this repo's `CLAUDE.md`, the docs work (a new `docs/architecture/` page plus a Trailmark-driven `docs/flows/` refresh) is included in this same effort, not deferred — confirmed explicitly with the user rather than assumed.
