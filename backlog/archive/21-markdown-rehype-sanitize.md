# 21: Markdown pipeline — add rehype-sanitize

**What to build:** Add `rehype-sanitize` to the shared rehype pipeline (`MARKDOWN_REHYPE_PLUGINS` in `src/app/items/markdown-plugins.ts`), positioned *before* `rehype-prism-plus/common`. This closes the gap where the pipeline's current XSS-safety depends implicitly on raw-HTML parsing simply never being enabled, rather than being enforced explicitly. The default sanitize schema already permits `className` on code elements, so the highlighter's `language-*` classes keep working without extending the schema — the highlighter runs after sanitization and injects its own markup directly into the already-sanitized tree.

**Blocked by:** None (can start immediately — unrelated to the Zod/error-handling dependency chain)

**Status:** done

**Completed:** on `feat/21-markdown-rehype-sanitize`

**Pull Request:** https://github.com/sgspinola/pensieve-archive/pull/4

- [x] `rehype-sanitize` added as a dependency
- [x] Added to `MARKDOWN_REHYPE_PLUGINS`, ordered before `rehype-prism-plus/common`. Note: `@uiw/react-markdown-preview`'s `nohighlight` entry point always appends `MARKDOWN_REHYPE_PLUGINS` *after* its own internal plugins (`rehype-slug`, `rehype-autolink-headings`, `rehype-rewrite`, `rehype-attr`), so `rehype-sanitize` actually runs on a tree that already contains the library's heading-anchor-icon and code-block-copy-button markup. The default schema alone stripped that markup (breaking both features) and desynced each heading's `id` from its anchor-link's `href` (via the default schema's `clobberPrefix`). Fixed by extending the schema in `markdown-plugins.ts` to explicitly allow that library-internal markup, plus a small scoped `prefixHeadingAnchorHrefs` rehype pass that rewrites each anchor `href` to match the `clobberPrefix`'d `id` sanitize is about to produce — added after `/code-review` flagged an earlier version of this fix that cleared `clobberPrefix` schema-wide, which would have weakened DOM-clobbering protection for every id/name on the page, not just headings. See the code comments in `markdown-plugins.ts` for details. `className` on code elements for syntax highlighting needed no extension, as expected.
- [x] Manual verification (plus a lightweight Vitest seam added: `src/app/items/markdown-plugins.test.ts`, rendering the real `@uiw/react-markdown-preview` component via `react-dom/server` — no jsdom needed) that code-block syntax highlighting still renders correctly under the new plugin order, across MarkdownEditor's Preview tab and ItemRow's read-only view (both share the same `MarkdownPreview` component and plugin list, so one render path covers both)
- [x] Confirmed markdown link `javascript:` URL stripping is unaffected — verified it's actually enforced by React 19's own built-in `javascript:`-URL guard on `href`/`src` at render time, not by `react-markdown`'s URL transform (`@uiw/react-markdown-preview` always overrides that transform with its own identity function unless the caller passes one, which this app doesn't). **Found affected, not unaffected as assumed:** `data:` URI images, which rendered before this change, are now stripped by `rehype-sanitize`'s default schema (`protocols.src` only allows `http`/`https`). No markdown content in this app was known to rely on `data:` image URIs; flagging here rather than silently expanding scope to special-case it back in.
